    JSON data structure¶

    The model as the engine stores it: the structure.json inside a .x2d file (see File Formats) and a plain .json export are this same object. You can write one by hand, or from any program, and open it in the application; it is also what the engine's save() and load() use (see Scripting with the engine).

    save() writes a single JSON object and load() reads it. Absent keys take their defaults, so a file stays readable as the format grows (for example, domain absent means plane).

    Top level¶

    The list below is written from the engine (what save() writes), so it has every list the file can hold and every field of its entries. A list is [ {fields} ], one object per entry, and a map is { id: {fields} }. A name followed by ? is written only when it has a value; … is a value that is not a flat record.

    {
  "domain": "plane" | "plate",
  "project_info": { … },
  "propagate_edge_supports": …,
  "propagate_edge_springs": …,
  "nodes": [ {"id", "x", "y"} ],
  "materials": [ {"name", "elastic_modulus", "unit_weight", "alpha", "unit_mass", "material_type", "poisson", "design"} ],
  "sections": [ {"name", "material_name", "b", "h", "area_override", "inertia_override", "inertia_minor_override",
                 "torsion_override", "wel_y_override", "wpl_y_override", "wel_z_override", "wpl_z_override",
                 "av_y_override", "av_z_override", "warping_override", "wt_override", "curve_y_override",
                 "curve_z_override", "profile_name", "angle", "shape", "tw", "tf", "rc_cover", "rc_alpha_s",

    Triangles, quads and objects have each their own lists. A load or a spring on an area element is kept in the list of the kind of element it acts on: tri_* for a triangle (keyed by tri_id), quad_* for a quad (keyed by quad_id) and surface_* for a meshed surface object (keyed by object_id). So tri_area_loads, quad_area_loads and surface_area_loads hold the same kind of entry (a pressure pz on a tri_id, a quad_id or an object_id), and likewise the edge loads, the temperature loads and the area springs. Bars and line objects have distributed_loads and line_distributed_loads, and so on.

    Entries inside other entries¶

    // one phase of a construction sequence (an entry of `phases`)
{"id", "operations", "active_elements", "applied_cases", "case_factors", "support_set_id", "inherits_from", "reapply_self_weight", "release_supports", "time", "initial_state"}
// one operation of a phase (an entry of `operations`)
{"id", "action", "target", "group_kind", "ids", "factor", "note"}
// one support set (an entry of `support_sets`)
{"id", "description", "restraints", "assignments", "node_springs", "element_springs"}

    In a .x2d file the list is split. structure.json has everything above except support_sets, variants, variant_combinations and construction_sequences, which are in variants.json and sequences.json, and the decisions of the beam-bars detailing, which are in beam_detail.json (see File Formats). A plain .json export has them all in one object.

    Notes on the slots¶

    • The three per-node components are positional: they are written with the canonical (plane) names ux/uy/tz, fx/fy/mz, kx/ky/kt in both domains. In a plate model read them as w/θx/θy, fz/mx/my, kz/kθx/kθy. Readers also accept the plate aliases on input.
    • geometry_objects[].kind is one of segment, arc, multisegment, rectangle, polygon (the old spellings line, polyline, surface are still read). The objects are node-driven: they carry node_ids and their parameters, and the geometry is in the nodes.
      • A curve (segment, arc, multisegment) has id, section_name, divisions, max_chord, loads, intersect_crossings, is_column, sd_ky, sd_kz, sd_klt, sd_ltb, beam and node_ids. A multisegment also has closed, and span_divisions when it was set.
      • A surface (rectangle, polygon) has id, tri_section_name (a triangle or a quad section), target_size, prefer_quad, edge_support_mode, edge_spring_mode and node_ids, and edge_supports (one support name or "free" per edge, in perimeter order) when it was set.
    • tri_sections[].formulation is CST, Allman or ES-FEM (panel / membrane) in the plane domain, or a plate-bending element in the plate domain: MITC3 (shear-deformable, the default — valid for thin and thick slabs) or DKT (thin-plate / Kirchhoff).
